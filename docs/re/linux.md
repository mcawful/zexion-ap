# The Linux build

Zexion's Linux binary (`builds.md`, "B1 on Linux") against what `memory.md` records for the
Windows exe. The Linux binary keeps its symbol table and loads at fixed addresses, so a global
is found by its name and a field by its offset from that name; the Windows exe has neither, so
its targets were found by byte pattern. Every address on this page is a link address of the
Linux binary, which is where it is at run time (it is `ET_EXEC`; seen in the game: "Read from
the running game").

Every target of `client/patterns.py` is mapped. Most facts here are from the binary on disk;
"Read from the running game" records what has been read from the game itself (through the Linux
helper, `native/README.md`), and "Reading the running game" is from the test PC and a stand-in
game. The disassembly is GNU `objdump -d -C
-M intel` of a copy in `lab/linux-b1/` (`all.asm`), which names each rip-relative operand as
`symbol+offset`.

### What differs from Windows

- **The shift holds well beyond the four checked fields.** These Linux reads land exactly at the shifted Windows addresses:
  - the item pool (`+0x79E990`) and the object pool (`+0x388DA0`) with their next-free counters;
  - the message slots (`+0x8C6B48`);
  - the death count (`+0xAD4`);
  - the second per-cell map byte (`+0x15B69`, Windows `+0x3E5209`, in the pickup at `0x642960` and in `createUpgrade`);
  - the color slot table (`+0x137FF`, Windows `+0x3E2E9F`);
  - `fade_level` (`+0x138A3`, read by `setSpritePalette`);
  - `frame_clock` (`+0xB0`, read by the item spawn and zeroed in `init()` next to the `save_loaded` stores);
  - `last_message` (`+0x13350`, with the sequence number at `+0x13358` compared to `[p+0x1D8]` by `verifyIndexedSpritePtr`).

  The Lookup records `last_message` and `frame_clock` as measured on this evidence. `gGameState` holds no `wchar_t` or `long` fields up to at least `+0x8C6B48`. The pools are reached by `lea reg,[rax+disp]` plus `gGameState`, so `objdump` names no symbol for them: search for the raw displacement as well.
- **The structure sizes and offsets match MSVC's:** SpriteRec `0x1D8` (the template copy), item object `0x3B0`, general object `0x5C8`, message slot `0x1628`, item record 100 bytes. These fields are at the same offsets: sprite `+0x198`, `+0x1A0`, `+0x1A8`, `+0x1B0`, `+0x1BC`, `+0x1C4` and `+0x1D8`; message `+0x1EC`, `+0x1FC`, `+0x200`, `+0x204`, `+0x214`, `+0x218` and `+0x220`; glyph cut `+0xD8` to `+0xF0`; player `+0xA4C`, `+0xB30`, `+0xBB8`, `+0xCBC` to `+0xCC2`, `+0xCEA`, `+0xCEC`, `+0x103C`, `+0x108E`, `+0x10D8`, `+0x1100` and `+0x1108`. The item looks' general-object and other sprite fields (`+0x30`, `+0x40`, `+0x48`, `+0x120`, `+0x1D0`; `+0x1E8`, `+0x210`, `+0x211`, `+0x32C`, `+0x32E`) also match: "Mapped by disassembly: item looks".
- **The globals outside `gGameState` are simply named symbols** (`gPowerUpDefs`, `gSpriteWorldP`, `gMasterSpritesP`, `gSpriteDrawProcs`, `gGameSoundManager`, `gEditorMode`, `gCursorMode`, `gPreferences`). None is at a shifted address.
- **ABI and code differences the Linux helper must handle:**
  - `updateNumberDisplay`'s third bool: pass 1.
  - `popup_width_code`'s opcode `0xBE`.
  - `text_cut_code`, which must be rebuilt for the -O0 stack-local code. It has 14 bytes, and the mod-9 branch is extra.
  - No allocator slots are needed.
  - The weapon-strip gate is a preference that defaults to 1.
  - `menu_state` is the cursor mode, and the mouse can set it to 1.
- All the code is unoptimized GCC (frame pointer, locals in `[rbp-…]`). Calls are direct `call rel32` to named functions, so these function targets need no byte patterns: the binary is `ET_EXEC` and keeps its symbols.

### What differs from Windows

- **Struct offsets agree** wherever checked: widget (`+0x1D8` panel, `+0x1E0` index, `+0x1E8` rect, `+0x1F0` label, `+0x1F8` record, `+0x230` code/slot, `+0x2C0` callback, `+0x2C8` handler), panel (`+0x1E0` children, `+0x1E8` capacity, `+0x1EC` selectable, `+0x1F0`/`+0x1F8` sprites, `+0x200`/`+0x260` frames, `+0x278` pieces, `+0x2B8` width, `+0x2DC` selected, `+0x2E4` index, `+0x2F8` handler), menu (`+0`, `+8`, `+0x20`, `+0x68`, `+0x70`, `+0x78`, size `0x80`), text (`+0x1D8`, `+0x1DC`, `+0x1E0`, `+0x1E4`, `+0x1E8`, `+0x1EC`, `+0x228`, `+0x230`, `+0x238`, `+0x248`, size `0x268`), sprite (`+0x30`, `+0x98`–`+0xD0`, `+0x148`, `+0x1A8`, `+0x1BC`, `+0x1C4`), layer (`+0x18`/`+0x20`) and the randomizer menu block. So nothing before those offsets changes size between the ABIs. Fields past them were not checked.
- **Calling convention:** every function the helper calls (`createGameMenuItem`, `moveGameMenuItem`, `moveSpriteString`, `SWChangeMasterSprite`, `addGameMenu`, `alterSpriteString`, `newSpriteString`, `addSpriteString`) is SysV; `createGameMenuItem` puts its last three arguments on the stack where Windows puts five. Typed C++ function pointers compiled for Linux handle it; any hand-written thunk must not assume the MS layout.
- **Callbacks take no arguments on Linux** (`void(*)()`, called bare by `StandardMenuAction`), while the helper's Windows wrappers are typed `(widget, event)`; wrappers in the callback slot must not use them. Handlers (panel and widget) do get `(GameMenuItem*, int)` in `rdi`, `esi`.
- **Code patches need new bytes:** `keys_branch` is `75 3C` at `0x618A7E` (Windows `75 2E`). The other group-B targets are function entries and data, so no patch bytes.
- **Two divergences from memory.md:** the equipment screen's panels 5 and 6 have other handlers on Linux; `text_set_fn` has an identical twin. Neither affects how the helper uses them.
- **Fixed addresses:** all of these are link addresses in an ET_EXEC binary, so the Linux helper can take them from the symbol table (`nm`) rather than byte patterns; the code bytes quoted above are from the B1 copy only.

### What differs from Windows

- **The Linux build is unoptimized** (GCC 9.4, `rbp` frames, every value reloaded from memory, nothing inlined). Every code-patch target must be re-derived: the Windows byte checks and patch shapes (the 50-byte seen-marker rewrite, the `FF 15` + `mov rdx` ending check, `cmp cx, r12w` in the ailment tests) do not match. The upside: no live registers across the patch sites (only stack locals), so jumps over stretches are easier to check.
- **Steam calls go through game wrappers.** All 23 achievement sets go through `setTheAchievement(int)` `0x5459E3` (and clears through `clearTheAchievement(int)` `0x545A38`), each calling `SteamUserStats()` (not inlined). So hooking `setTheAchievement`/`clearTheAchievement`, or the one accessor, is an alternative to the GOT slot on Linux.
- **Several Windows globals map onto named Linux globals outside `gGameState`**, with layouts that match where checked: `gExitActionP`/`gExitDelay`/`gExitActions`, `gAreaEvents`/`gAreaEventCount`/`gAreaEventProcs`, `gMoveProcs` (entry 120), `gSmallTexts`, the `rStartingLocation*` arrays, `gRandoPreferences` (= `randomizer_menu`), `gGameUnlocks` (= Windows `+0xCDFC80`: Feat bytes at `+0x43E`, `+0xCE00A8` at `+0x428`). Not by a fixed shift: by name and code.
- **Side corroborations of the other groups' targets:** `forceSeed`'s `[gLastGameMenuP]+0x20` matches Windows' `current_menu` (`+0xDF82F8`) use, as the menus section finds `current_menu` to be `gLastGameMenuP` `0x12F5700`. `EndingCutscene` sets flag 251 at `gGameState+0x1E8` and flag 250 at `+0x1E7`, which agrees with `flags` = `gGameState+0xED` by the shift. `weaponCool`'s tests agree with `ailments` = `gGameState+0x13724`.
- **ABI.** Handlers and game functions take SysV arguments (`rdi`, `rsi`, `rdx`, …): the area-event handlers `(char row, char col, AreaEvent*)`, `forceSeed()` and `generateRando()` take none. `wchar_t`/`long` play no part in any group-C struct: the area events, Text entries, start table, section and Steam context are byte, short, pointer or file-defined.
- **Not in memory.md:** `weaponCool` has a third timer under the same AILMENTS rule, player `+0xDA0` (`0x5081C2`..`0x5081FB`: 3 a frame at 1, zeroed at 2). Whether the Windows build has it too is unknown; the trap patches don't need it.

### Where the translation layouts differ from Windows

- **Characters are 4 bytes everywhere.** `loadTextFile` widens each UTF-16 unit of a translation file to a 4-byte `wchar_t`, with no surrogate decoding. So the SmallText, LargeText, ItemNames, Database, Config and Controls buffers hold 4-byte characters, and every offset table counts 4-byte characters (`setupTextList`'s `[rax*4]`). The entry and offset values match Windows for the same file. Byte addresses double: text + offset×4. Room per entry, in characters, is unchanged, but the bytes double. The icon characters are 32-bit: `U+E024`+ is `byte + 0xDF64` (`0x642BEA`), with `0x6E` giving `0xE04F` and `0x77` giving `0xE050`. The parser cuts at `----` as on Windows.
- **What the helper's `translation.cpp`/`.h` needs on Linux, and has:** `sizeof(wchar_t)` reads and writes (`read_text`, `write_text`, `writable(... * sizeof(wchar_t))`), correct as the helper is built with GCC's 4-byte `wchar_t`; no code there assumes 2-byte units. `tr::kSize` is `0x40150` on Linux, not `0x40138`. Struct offsets `+0x00`–`+0xD0`, the `hd::` and `message::` namespaces and the `hdlabel::` offsets the helper uses are all unchanged. `FontMetrics`' glyph records are not: `0x40` bytes with 64-bit fields, which it reads on Linux ("Mapped by disassembly: the helper's translated text").
- **Strings passed to the game:** `generateText` takes a libstdc++ `std::__cxx11::wstring` by hidden reference, and the caller must destroy it. Windows' `hd_build_fn` takes an MSVC `std::wstring` and frees it itself. The helper's Windows pattern (build with `wstring_new_fn` on 32 zero bytes, then hand over) does not carry over. On Linux: construct (`0x492582`, or the helper's own libstdc++ `wstring`), call, then destroy (`0x492556`).
- **`hd_text_fn` arguments:** use the SysV order. Pass the same six ints the game passes with the popup (24, 160, 88, 100, 1, 180), not zeros: Linux reads ints 2, 5, 6 and 7. Entry and kind are `short`, each in its own 8-byte stack slot, and the message is the 4th stack slot.
- **Unchanged:** the HD message objects (`0x238`, fields `+0x20C`/`+0x210`/`+0x220`/`+0x228`/`+0x22C`/`+0x230`), the message slots (`0x1628`; `+0x1D8`, `+0x1E0`, `+0x1EC`, `+0x1620`, `+0x1624`), the label's translated glyphs (`+0x230`, `+0x238`, `+0x240`, `+0x244`, `+0x248`, `+0x24C`, `+0x258`, `+0x260`), and `message_slots` at exactly the gGameState shift.
- **The counts:** these are separate named int16 globals (`gSmallTextCount`, `gLargeTextCount`, `gPowerUpDefCount`, `gDatabaseEntryCount`). They are not where the shift would put them, and they are not next to the Windows neighbors.

### What differs from Windows

- **The font's glyph records are twice the size.** `[font+8]` holds `0x40`-byte records, and the
  builder takes a glyph's advance from its `+0x20` less its `+0x10`, both 64-bit. Windows'
  are `0x20`-byte records with 32-bit values at `+0x08` and `+0x10`, so `FontMetrics` reads the
  Linux layout on Linux (`kGlyphEntry`, `kGlyphFrom`, `kGlyphTo`, `GlyphField`;
  `native/linux/tests/translation_tests.cpp` reads a glyph's advance from such a record, and
  fails with the Windows layout): with Windows', the popups' wrapping and centering
  (`layout_popup`, `centered_lines`) would be wrong for every font glyph; the space and the
  icons, whose advances come from elsewhere, would not. The records are FreeType's glyph metrics, `long` fields
  (inferred, above).
- **The builder drops what does not fit.** Its loop stops once the glyph count reaches `+0x240`,
  so characters past the label's room are not built at all. `memory.md` has Windows laying them
  over the last glyph. The helper never builds past the room.
- **The centering's widening stops at a hidden glyph,** across and down. Down, it also compares
  a glyph's top with its quad's first x (`+0x98`). The first does not matter for a text the
  helper has just built, every glyph of which is shown. The second can make the game's top of a
  text differ from `vertical_extent`'s. `keep_middle` measures the old text and the new one the
  same way, its own, so it keeps the middle by that measure; whether that puts the Feats title
  where the game's own centering would is not worked out.
- **Named on Linux:** the attach is `generateSimpleTextForMenuItem`, the centering across is
  `centerTranslationSpriteString`, down is `verticalTranslationSpriteString`, and the label
  layout is `moveSpriteString`. The game-mode panel is built inside `SaveFileMenu()`, and the
  prompt with Skip Escape and Final Battle? is `SkipFinalEscapeOptionMenu()`.
- **Not in `memory.md`:** `refreshPauseFromOption` centers the pause row's attached text across
  (with 0.0) after attaching it, which the helper's rebuild of the count does too (`pause.cpp`,
  `.center`). Whether Windows' `0x168910` does the same is not recorded.
- **Unchanged:** the constants `rebuild_label` uses (−1.0, 160, 2.0, 4.0, the corners `+0x98`,
  `+0xA0`, `+0xA8`, `+0xC0`), the `hdlabel::` offsets and size, the wrap widths, the space and
  scale, the factor `+0x40060`, the icon characters' frames and sheets, and the mark.

### What differs from Windows

- **The branch's bytes:** `75 3C` (`jne +0x3C`), not `75 2E`; the patch is the same one byte,
  `75` to `EB`. `pause.cpp` keeps the Linux pair off Windows.
- **The panel's arrays come from `calloc`,** not `malloc`, both glibc's, and the game frees them
  with glibc's `free` (`removeGameMenu`). The helper's arrays and frees are glibc's too, with no
  need for the GOT slots (`equip.cpp` calls `std::malloc` and `std::free` off Windows).
- **Callbacks take no arguments** (`StandardMenuAction`'s bare call, "Mapped by disassembly:
  menus and UI"): the EQUIPMENT wrapper must not use its arguments. Handlers and the way back
  (`+0x68`) do get theirs, in `rdi` (and `esi`).
- **Not in `memory.md`:** `EquipmentMenu` sets the pause screen's `+0x68` to
  `refreshPausePalette` (`BasicReturn`, then `setSpritePalette(7, 0x11)`) before it builds
  (`0x5E331A`–`0x5E3328`), and its own screen's to `EquipmentMenuReturn` (`0x5E72A6`–`0x5E72AD`).
  The helper's wrapper is only on the pause screen's `+0x68` while OPTION MENU is open over it,
  when EQUIPMENT cannot be chosen, so the store does not meet it. Whether Windows' `0x12BA90`
  does the same is not recorded. The description box's child 1 is created with index 0, as
  child 0; the helper reads them by place.
- **Unchanged:** every offset, count and place the helper uses (the widget's `+0x1D8` to `+0x2C8`,
  `+0x1E4` and `+0x1E6`, the panel's `+0x1E0` to `+0x1F8`, `+0x2C6`, `+0x2E4`, `+0x2F8`; the 7
  panels; 3, 0x11 and 0x88 glyphs; events 0 and 3; `+0x230`; definition 34 and the record's
  frame; the 2 panels, 9 sprites and 4 glyphs of the KEYS row; frames 384 to 387; 144, 208 and
  the icons' places; the sprite's `+0x128`, `+0x148`, corners and `0x38`-byte frames; `+0x68`
  with the menu; 32-byte Text entries).

## `gGameState` has the Windows layout

| Field | |
|---|---|
| Value | `gGameState` (`0x9E7840`, `0x8CCCF8` bytes, in `.bss`) holds the state the Windows build keeps from `+0x3CF6A0` of its image, offset for offset, for every field checked: first four, by `LoadGame`'s stores, then many more (below). `LoadGame` stores the save's ITEMS counter at `gGameState+0xAC8`, its major-item list at `+0xAE0`, its randomizer marker at `+0x13738` and its map grid at `+0x14FFD`; the Windows build keeps the same four at `+0x3D0168` (`pickup_counter`), `+0x3D0180` (`pickup_list`), `+0x3E2DD8` (`rando_marker`) and `+0x3E469D` (`map_grid`), and each Windows address less its Linux offset is `0x3CF6A0`. ## Reading the running game

| Field | |
|---|---|
| Value | **The client can't read the game itself.** Reading another process's memory on Linux (`/proc/<pid>/mem`, `process_vm_readv`) takes the kernel's ptrace permission. With Yama's `kernel.yama.ptrace_scope` at 1, the default of many distributions, a process may read only its own descendants, and the game, started by Steam, is not the client's. The test PC has the scope at 1: there a process that was not a stand-in game's ancestor was refused its `/proc/<pid>/mem` (`EACCES` on opening it). So the Linux helper reads the game's memory for the client, from inside it (`read`: `native/README.md`, "The Linux helper"), and opens it to no other process, whatever the scope. |
| | **Superseded: opening ptrace while a client is connected.** The helper's first design called `prctl(PR_SET_PTRACER, PR_SET_PTRACER_ANY)` while a client was connected and `PR_SET_PTRACER` 0 when it left. With the stand-in game, a process not its ancestor was refused its memory before a client connected, read it while one was, and was refused again after. It was replaced the same day, after review: the window let every process of the user in, not just the client, and by the kernel's rules (assumed: `/proc/<pid>/mem`'s permission is checked when it is opened, and an attach outlives the window) what one opened in the window stayed open after it. |
| | **Pids.** Flatpak's Steam runs the game in its own process-id namespace, so that its pid inside differs from the one in the host's `/proc` (both are in `/proc/<pid>/status`, `NSpid`): seen with the game ("Read from the running game"). |
| Status | measured (the test PC's ptrace scope, and the refusal, with the stand-in game, 2026-11-18; the pid namespace, with the game, the same day); superseded (the first design's window, measured with the stand-in game the same day); assumed (the kernel's rules behind the window's flaw) |
| Method | `cat /proc/sys/kernel/yama/ptrace_scope`; `tests/test_native_linux.py`, `test_the_games_memory_is_never_opened_to_other_processes` (and, for the first design, the test it replaced, `test_memory_is_readable_only_while_a_client_is_connected`); a by-hand read of `/proc/<pid>/mem` from a new session (`setsid`), which printed `errno 13 Permission denied` |
| Build | any (the stand-in game, not Zexion) |
| Evidence | The scope read `1`, 2026-11-18; the tests passed on the test PC the same day. |
