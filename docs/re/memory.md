# Memory

Where the running game keeps the state the client and the helper use. Addresses are
module-relative (`+0x…` is `Zexion.exe+0x…`) and build B1's only: code finds them by byte
pattern ("Byte patterns" below), never by these numbers. Map cells are this repo's (x, y), or
as the game shows them (X37 Y18, "Pulsava 37,18"); axes and directions per `randocells.md`,
"Grid order". Format and statuses per [`README.md`](README.md).

## A pickup counter updates the instant an item is collected

| Field | |
|---|---|
| Value | `+0x3D0168` (`pickup_counter`, 16-bit: the code reaching it uses word-sized `dec`, `movsx` and `mov`) is the pause screen's `ITEMS: x/150` count; the save keeps it at file `0x935A` (`save-format.md`, "Counters"). It went 0 → 1 at the first pickup in slot 30 and 1 → 2 at the second, at the moment of collection (within 0.1 s, the sampling interval), with no pause or save; it read 1 with one pickup made, and live and saved agreed (1) with slot 28 loaded; the owner's far-along slot 1 holds 150 (ITEMS 150/150). Not every item counts, and a grant does not move it ("Granting each kind of item, and what keeps it"). It says that something was collected, not which location: checks come from the map grid. |
| Status | measured |
| Method | `tools/memscan.py snap --module-only` twice while standing still, then a 10 Hz recorder over the module logging bytes that had been stable; the first pickup by snapshots, the second by the recorder |

## The live map grid flips at the moment of pickup

| Field | |
|---|---|

So only `0x1B` counts as collected, and a client detects a collected location by polling the location cells. ## Granting each kind of item, and what keeps it

| Field | |
|---|---|
| Value | For the weapon and the key tried, the inventory byte was the whole grant. For counted items it is not: the energy, missile and bomb numbers the game plays with are separate 16-bit fields of the player state (`+0x3EC3F0`): current energy `+0xCEA`, max energy `+0xCEC`, current missiles `+0xCBC`, max missiles `+0xCC0`, current bombs `+0xCBE`, max bombs `+0xCC2`. |
| | **Three places set them**, from disassembly. The player state's setup (RVAs `0x1E35F4` to `0x1E36F2`, in the function at `0x1E1030` that also holds the player's reset, `0x1E372F`) writes 3 Energy Tanks, 3 Missile Containers and energy `0x30`/`0x30`; a randomizer game's starting inventory comes from its section ("Starting a new game"). Loading a save (RVA `0x9C630`) reads current energy and missiles from the save (`save-format.md`, "Current energy and missiles") and recomputes every maximum from the counts. The pickup routine (RVA `0x1EECB`) increments the item's byte (`0x1F1D8`); sets max missiles to Missile Containers + 10 × Missile Boxes (items 1 and 36) and adds the difference to current missiles; does the same for bombs (Mega Bombs + 10 × Bomb Boxes, items 2 and 37); and if Energy Tanks × 16 exceeds max energy, sets max and current energy to it. It then passes current missiles and bombs to the HUD's own number objects (`+0xB30` and `+0xBB8`, function `0x1F5B10`, which stores the value as a double at object `+0x48`). Several other routines subtract from `+0xCEA` (for example RVAs `0x1E827` and `0x1DCC43`, the damage routine: "DeathLink"). |
| | **The pickup counter** (`0x1F1A1`) counts every item except IDs 27 to 31 (the Alpha, Beta, Gamma and Omega Keys, and Zexion: its grab left the counter unchanged, "The goal: Zexion's inventory byte at the grab") and 38 to 45 (the eggs, the Data Disc, "Gamma key no rando"), going by the item ID in the item's record, the same ID whose byte it increments; names from the item records (`Objects`; `ItemNames.txt` differs for 26 and 37, `save-format.md`). |
| | **Granted live** in slot 28, one at a time, the player standing still in a save room:<br>• **Energy Tank** 5 → 6 alone: nothing changed on screen, and no other player-state field moved. Then max and current energy 80 → 96: the HUD and inventory showed a sixth tank, full.<br>• **Missile Container** 3 → 4, max missiles 3 → 4, current 2 → 3: max 4 at once and missiles fired; the HUD number stayed at the old value until the next shot.<br>• **Force Blaster** (item 4) 0 → 1, the byte alone: in the weapon list, and it fired.<br>• **Alpha Key** (item 27) 0 → 1, the byte alone: shown on the pause and map screens.<br>• **Mega Bomb** 0 → 1, max and current bombs 0 → 1: in the inventory, but no HUD icon appeared (the HUD layout call does that: "Game functions the helper calls"). |
| | **What keeps a grant.** The first four grants survived a room change, a save, and quitting to the title and loading the slot again: the saved file held the inventory bytes, current energy 96 and current missiles 4, and after the reload the player state read energy 96/96 and missiles 4/4. The Mega Bomb, granted after that save, was gone when the player died and continued without saving: its byte went 1 → 0 at the moment of continuing. So a grant lasts only once the game has saved it, and a death returns to the last save. No grant moved the pickup counter (1 throughout): a grant does not run the pickup routine. |
| Status | working in game (Energy Tank and Missile Container with their fields, Force Blaster: granted, used, and kept through a room change, a save and a reload, 2026-10-21); measured (the Alpha Key shown and kept likewise; the Mega Bomb without its HUD icon, and lost on a death without a save; the routines, by disassembly); superseded (not tried then: a granted key on its gate, done in "Keys, the gates and the key markers"; the HUD objects, written by the helper since: "Game functions the helper calls"); open (an area load other than one room change) |

## The loaded save's randomizer section is at +0xCDD6D0

## Telling play from menus, the title screen and death

| Field | |
