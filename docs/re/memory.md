# Memory

Where the running game keeps the state the client needs. Addresses are module-relative
(`Zexion.exe+offset`) and good for build B1 only; code finds them by the byte patterns in
"Byte patterns" below (`client/patterns.py`), never by these numbers. Format per
`docs/re/README.md`.

## A pickup counter updates the instant an item is collected

| Field | |
|---|---|
| Value | `Zexion.exe+0x3D0168` counts pickups in the current session: it went 0 → 1 at the first pickup in slot 30 and 1 → 2 at the second, at the moment of collection (within 0.1 s, the sampling interval), with no pause or save involved. Its neighbors read as a record of 32-bit fields. It is a 16-bit value (the code reaching it uses word-sized `dec`, `movsx` and `mov`), the pause screen's `ITEMS: x/150` count (it read 1 with one pickup made, and a granted item did not change it). The save keeps it as a 16-bit value at file `0x935A`: live and saved agreed (1) with slot 28 loaded, and the owner's far-along slot 1 holds 150, matching ITEMS 150/150. It says *that* something was collected, not *which* location, and not every location counts: the pickup routine skips items 27 to 31 and 38 to 45 ("Granting each kind of item, and what keeps it"). A client detects checks from the map grid instead. |
| Status | measured |
| Method | `tools/memscan.py snap --module-only` twice while standing still, then a 10 Hz recorder over the module logging bytes that had been stable; the first pickup by snapshots, the second by the recorder |
| Build | B1 |
| Evidence | Snapshots `lab/mem/s30-*` (first pickup; deleted after analysis, 1.1 GB) and `lab/mem/p2-before*`, log `lab/mem/p2-record.log` (second pickup at about 9.1 s), 2026-10-20. |

## Granting each kind of item, and what keeps it

| Field | |
|---|---|
| Value | For the weapon and the key tried, the inventory byte was the whole grant. For counted items it is not: the energy, missile and bomb numbers the game plays with are separate 16-bit fields of the player state (`+0x3EC3F0`): current energy `+0xCEA`, max energy `+0xCEC`, current missiles `+0xCBC`, max missiles `+0xCC0`, current bombs `+0xCBE`, max bombs `+0xCC2`. Three places set them, from disassembly. New-game setup (RVAs `0x1E35F4` to `0x1E36F2`) writes 3 Energy Tanks, 3 Missile Containers and energy `0x30`/`0x30`. Loading a save (RVA `0x9C630`) reads current energy and missiles from the save (`save-format.md`, "Current energy and missiles") and recomputes every maximum from the counts. The pickup routine (RVA `0x1EECB`) increments the item's byte (`0x1F1D8`); sets max missiles to Missile Containers + 10 × Missile Boxes (items 1 and 36) and adds the difference to current missiles; does the same for bombs (Mega Bombs + 10 × Bomb Boxes, items 2 and 37); and if Energy Tanks × 16 exceeds max energy, sets max and current energy to it. It then passes current missiles and bombs to the HUD's own number objects (`+0xB30` and `+0xBB8`, function `0x1F5B10`, which stores the value as a double at object `+0x48`). Several other routines subtract from `+0xCEA` (for example RVAs `0x1E827` and `0x1DCC43`); that this is damage is assumed. The pickup routine increments the pickup counter (`0x1F1A1`) for every item except IDs 27 to 31 (the Alpha, Beta, Gamma and Omega Keys, and Zexion: its grab left the counter unchanged, "The goal: Zexion's inventory byte at the grab") and 38 to 45 (the eggs, the Data Disc, "Gamma key no rando"), going by the item ID in the item's definition record, the same ID whose byte it increments; names from `ItemNames.txt`.<br>Granted live in slot 28, one at a time, the player standing still in a save room:<br>• **Energy Tank** 5 → 6 alone: nothing changed on screen, and no other player-state field moved. Then max and current energy 80 → 96: the HUD and inventory showed a sixth tank, full.<br>• **Missile Container** 3 → 4, max missiles 3 → 4, current 2 → 3: max 4 at once and missiles fired; the HUD number stayed at the old value until the next shot.<br>• **Force Blaster** (item 4) 0 → 1, the byte alone: in the weapon list, and it fired.<br>• **Alpha Key** (item 27) 0 → 1, the byte alone: shown on the pause and map screens.<br>• **Mega Bomb** 0 → 1, max and current bombs 0 → 1: in the inventory, but no HUD icon appeared.<br>The first four grants survived a room change, a save, and quitting to the title and loading the slot again: the saved file held the inventory bytes (`0x92F3 + ID`), current energy 96 and current missiles 4, and after the reload the player state read energy 96/96 and missiles 4/4. The Mega Bomb, granted after that save, was gone when the player died and continued without saving: its byte went 1 → 0 at the moment of continuing. So a grant lasts only once the game has saved it, and a death returns to the last save. No grant moved the pickup counter (1 throughout), as expected: a grant does not run the pickup routine. |

## The loaded save's randomizer section is at +0xCDD6D0

| Field | |
|---|---|
| Value | When a save loads, the game copies its randomizer section, 0x908 (2,312) bytes from file offset `0x12814` (location list, 4 zero bytes, item table at `+0x26C`, settings), to `Zexion.exe+0xCDD6D0`; the generator and the settings code read it there. The per-slot copies are at `+0x347830 + (slot − 1) × 0x908` (slot 30's is the `+0x357E18` mirror above). With slot 28 loaded, all 2,312 bytes at `+0xCDD6D0` equaled `Save Game 28.sav` from `0x12814`. **Only a randomizer save replaces it.** The load routine copies the section only when the save's randomizer marker (file `0x9402`, 16-bit; 1 in every randomizer save, 0 in normal ones, `save-format.md`) is 1 (`cmp word [block+0x9400], 1` at RVA `0x9C662`; a slot's block starts at file offset 2, so block `+0x9400` is file `0x9402`), and then stores the marker at `+0x3E2DD8` (`0x9C91C` to `0x9C923`). Watched live on 2026-10-22, in three runs. First (the section only): slot 7, slot 28, the owner's normal slot 25, a new normal game, slot 7. The section switched to slot 28's seed, stayed slot 28's through slot 25 and the new normal game, and switched back with slot 7. Then (the marker too): slot 7 (marker 1), slot 25 (the section stayed slot 7's while the marker went to 0), slot 28 (1), slot 7 (1). A third run: slot 7 (marker 1), then a new normal game: the marker went to 0 about 0.7 s before the game read in play, while the section stayed slot 7's; it had also read 0 at the title right after start-up. So the section means something only while the marker reads 1; `client/session.py` checks it, and `client/patterns.py` finds it (target `rando_marker`). |

| Field | |

## Keys, the gates and the key markers

| Field | |
|---|---|
| Value | **The gates read the key bytes.**<br>&nbsp;&nbsp;– The key check is a state in the game's object scripts (the `Enemies` file, 0x6C-byte states; state type 31, handler `0x52200`, op 11 at `0x526F8` to `0x52770`). It reads the four key inventory bytes (player state `+0x10A9` to `+0x10AC`, items 27 to 30) and nothing else.<br>&nbsp;&nbsp;– In a normal save (marker `+0x3E2DD8` not 1) all four keys are needed. In a randomizer save it depends on Gates, `2 × t73 + t72` (the settings bytes 72 and 73): **Off**, never passes; **Vanilla**, all four keys needed; **Unlocked** and **Open**, the key check passes without keys.<br>&nbsp;&nbsp;– Each gate also marks itself visited after its key check, in flags 304 to 307 (one per gate). With Unlocked, a second check (op 12, `0x52775` to `0x52806`) passes only once at least two of those flags are set, so under Unlocked a gate needs no keys but needs two gates visited. With the other settings an event chain (3774 → 3761 to 3765) sets all four flags 304 to 307, so the second check never holds a gate back. All of the Unlocked and Open reading is from disassembly only.<br>&nbsp;&nbsp;– The states holding the key check are 14059, 14160, 14177 and 14195, of object types 2057, 2081, 2083 and 2086. Which rooms those objects stand in was not found.<br>**A key's pickup event only hides its map marker.**<br>&nbsp;&nbsp;– The pickup runs the item record's area event, 3382 to 3385 for the four keys. It is type `0x17`, handler `0x136A0`, from the table at `+0xCDD090`, which `0x17940` fills at start-up. Its effect is `flag[40 + 2k] = 0xFF` for key `k` = item − 27.<br>&nbsp;&nbsp;– The flags are a 0x9C4-byte array at `+0x3CF78D`, saved at file offset `0x0002 + flag`.<br>&nbsp;&nbsp;– Flags 40 to 47 hold each key's map marker as a (y, x) cell. ## Byte patterns

| Field | |
|---|---|
| Value | Thirty targets: the first eight below, eleven for helper phase 2, and eleven for helper phase 3. Each is found by two or three patterns from different code; `client/game.py` requires every pattern to match exactly once in `.text` (overlapping matches counted) and all to lead to the same address, or it refuses to run. Except the function-start patterns (kind `at`, below), only instruction-pointer-relative references are used.
